# Teak strategic review, October 2026

Reviewer stance: an outside UI-framework reviewer, evidence first. Date of review: 2026-10-08.
Repo state reviewed: `master` at `c016060` (after the `kerf` PR #3 merge and the CI fix), with zunk at
`166979b` (after PR #18). Zig 0.16.0 and 0.17.0 were both used.

Everything labelled **measured** was run on this review's machine (aarch64 Linux, Vulkan device available,
Chromium with SwiftShader for the web). Everything labelled **inferred** was read from code or docs and not run.
Numbers from the landscape survey are secondary-source and flagged where unverified.

---

## 1. Executive summary

**Verdict: yes, continue, but narrow the claim and fix a short list of foundation defects first.**
Teak is worth maturing as a *small, Zig-native, LLM-drivable, WebGPU-on-web-and-native UI framework for
tool-style applications* (engineering tools, dashboards, agent consoles). It is not worth maturing as a
general-purpose GUI toolkit that competes with egui, Slint, Flutter or Compose on breadth. The design is
sound and unusually inspectable; the implementation is a fast, capable prototype with a handful of
structural gaps (text engine, text input, accessibility wiring, platform reach) that decide whether it
becomes a product.

### Three strongest reasons to continue

1. **The architecture is coherent and it paid off in practice.** One agent built a 14K-line, full-featured
   CAD front end (Kerf, `apps/teak`) on it in a day. The Model/Msg/update/view loop, the flat `[]Cmd` buffer
   carrying `Msg` values as data, and the three independent passes produced a working app on three hosts
   (web, X11, headless) from one `App`. The same cost measured on a CPU-only pipeline: 1,000 rows of
   (text, text, button) lay out and render-build in about 0.7 ms; 10,000 rows in about 7 ms.
2. **It has a real, defensible niche that nobody in Zig occupies.** The Zig GUI field (as of Oct 2026,
   secondary sources) is immediate-mode: dvui (mature, native + web, but WebGL-leaning and GL/SDL based), Knots
   (new, Vulkan/WebGPU, immediate-mode, no IME, no shaping), Dear ImGui bindings, raygui. Nobody ships an Elm-style,
   command-buffer, WebGPU-first framework. Kerf's bake-off already shows the footprint advantage: zig-teak
   was the smallest full-app GPU stack (about 334 KB brotli at ReleaseSmall including the engine, versus about 1.21 MB
   for rust-egui).
3. **The agent-DX story is genuinely differentiated and mostly real.** `llms.txt` (709 lines, audit-enforced
   against `src/teak.zig`), `TEAK_SNAPSHOT` (the GUI as grep-able text), golden snapshot tests with no GPU, and
   `zig build shot` (headless native PNG, **measured working here, byte-identical output on Zig 0.16 and 0.17**) form a
   closed loop an LLM can drive without a display. I found no other UI framework that ships this
   whole loop as first-class features.

### Three strongest reasons for caution

1. **Text is the weak foundation, and it is where real apps live.** (a) A hard cap: the text vertex buffer holds
   `glyph_cache.CAPACITY * 6` = **256 text runs per frame, and runs beyond that are silently not drawn** (measured:
   with 16x40 = 640 runs, rows past about 15 render blank; see section 3.5). Web has the same cap. A dense table exceeds
   it. (b) Text is rasterized per whole string and colour into one texture plus bind group per string, with a
   linear-scan 256-entry LRU, not a glyph atlas. (c) `TextField` is a fixed-capacity single-line byte buffer with
   no click-to-caret, no mouse selection, no UTF-8 awareness (issue #6); Kerf had to write its own `Editor`. (d) There is
   no wrap in core (issue #8), no shaping, no fallback fonts, one monospace face by default on Linux.
2. **Accessibility and IME are scaffolding, not features.** The a11y tree builder is good and a web DOM-mirror
   shim exists in zunk, but `teak.run` never calls `publishA11yTree` (measured by grep: no call in `src/run.zig`, none in
   the examples). Win32 has a UI Automation provider (read-only, Narrator-style) and X11 has none (no-op); neither is reachable through `teak.run`, and there is no action path from assistive tech. IME composition exists only on Win32;
   X11 and web return an empty `ImeState` (issue #7).
3. **Bus factor of one, and a thin platform matrix.** One author, 174 commits, 43 of them on a single day (2026-10-05) via
   agents. Windows is "compile-only" for several features (issue #5), there is no Wayland-native and no macOS backend, the
   CI runs Linux unit tests only (no GPU, no web, no Windows), and wgpu-native is pinned at v25.0.2.2 while upstream is
   at v29.0.x (secondary source). The framework also carries a second owned dependency, zunk, which is itself a young
   one-person tool.

## 2. Architecture assessment

### 2.1 What the design actually is

```
Model --view--> []Cmd (flat, tagged union, Msg-generic) --layout--> []Rect
   ^                                   |                                |
   +---------- update <-- Msg <-- hit-test (previous frame) ---------- render -> vertices -> wgpu / WebGPU
```

- `Cmd(Msg)` is a generic tagged union (19 variants: group/scroll/overlay/virtual_list push-pop pairs, text,
  rich_text, image, button, text_input, checkbox, radio, slider, divider, canvas, scene3d). Interactive variants
  carry a `Msg` **value**, so hit-test returns a `Msg` directly and no callbacks exist.
- The run loop (`Runtime.frame`) rebuilds the whole view and re-lays-out every frame (continuous rAF or Fifo
  vsync), then diffs `[]Cmd`, `[]Rect` and `TransientState` against the previous frame to skip the vertex rebuild and
  upload. Input is routed against the **previous** frame's layout (one-frame hit-test latency, documented).
- HARDLINE is the governance layer: 5 invariants, 8 named escape hatches (comptime stitching, TransientState,
  fixed-depth stack layout, Host layer, overlay layer, subscriptions, declarative effects, resources), a list of forbidden
  patterns, and a `zig build audit` that enforces the greppable half.

### 2.2 Soundness

Strong points:

- **The Msg-in-Cmd choice is the keystone and it is right.** It removes closures, makes the UI replayable and
  diffable as plain data, makes headless testing trivial (`snapshot.zig`), and gives LLMs a four-step recipe (field,
  variant, switch arm, `cb.*` call) that the compiler checks via exhaustive `switch`.
- **Pure passes over flat arrays are cache-friendly and cheap.** Measured CPU cost per full pipeline pass is far
  below a 16 ms frame budget for thousands of widgets (table in section 3.4).
- **Declarative side effects extend TEA without breaking it.** `Sub`, `effects`/`effectMsg` and `resources`
  are the same idea three times: the app declares, the runtime performs, the result returns as a `Msg`.
  This is the Elm `Cmd`/`Sub` split applied consistently and is the part Kerf validated (HTTP LLM calls, storage, files,
  paste/drop).
- **Validators (`validateComponent`, `validateHost`, `validateGpu`) give early, readable comptime errors.** Good Zig
  practice.

Weak points and debts:

- **"All state in Model" has a cost in widgets.** Text editing state, scroll offsets and list state live in the
  app's `Model`, in fixed-capacity arrays (`TextField(N)`, `ComponentList(Child, cap)`, `todo`'s `items_len: u16`).
  This is the honest cost of the paradigm: it is what makes snapshots and replays work, but every real text field
  needs an editing model (caret, selection, grapheme boundaries, undo, IME composition) *above* Model. Teak today
  ships the smallest possible version. The architectural question is whether a reusable `Editor` Model component (like the
  one Kerf wrote) can live in the library without violating HARDLINE. It can; it is a component, not a hatch.
- **Identity by command index is fragile for anything stateful.** HARDLINE forbids ID hashing; focus is matched by
  `Msg` value (`focus.indexOfFocusMsg`), and `ComponentList` carries explicit `u64` keys in the Model. That works, but it makes
  retained-by-identity features (animation of a specific row, scroll anchoring across insertions, IME target tracking across
  reorders) awkward.
- **Layout is "flexbox-lite".** Fixed/min sizes, align, justify, spacer, grow-only flex, scroll with zero basis.
  Missing: flex shrink (issue #8), text wrap, grid, min-content measuring, baseline alignment. Nesting is limited by a
  `FixedStack(_, 32)` guarded only by `std.debug.assert`: in ReleaseFast/ReleaseSmall (what the web ships) an over-deep tree is
  an out-of-bounds write, not a panic. **Inferred from code, not triggered.**
- **No retained caches means no incremental anything.** View, layout and render-build are O(n) every frame. That is fine
  to about 10k commands (measured below) and is what a virtual list is for, but there is no layout caching, no dirty subtree, and no
  event-driven idle: the loop wakes at display rate even when nothing changed (only GPU upload is skipped).
- **Adding a widget touches nine places.** `CLAUDE.md` lists the checklist (Cmd variant, layout measure and position, hit-test, render, snapshot, a11y role, `cmdsEqual`,
  Win32 UIA mapping, re-export plus `llms.txt`). The passes take `anytype`, so a missed arm is a silent wrong-rects or un-clickable widget, not a compile error. A comptime
  "every pass handles every variant" check (an exhaustive switch helper) would turn that class of bug into compile errors.
- **The frame diff is hand-maintained.** `cmdsEqual` in `run.zig` compares each Cmd variant field by field. Forgetting a field in
  a new variant yields stale pixels (the code comments say this already happened once with button style). It should be
  generated from the union by comptime reflection (which also makes the 0.17 reflection change a one-place fix).
- **Rendering is quad + whole-string-texture only.** Square corners, hard shadows only, no gradients, no rounded rects, no
  clip other than rect scissors, no animation system (there is a `frame_counter` and `Sub` timers, nothing else). That
  fits the "engineering workstation" look Kerf wanted; it does not fit "modern app" polish. SDF rounded rects and soft shadows are
  a day of shader work each and do not touch the architecture.

### 2.3 Scalability by concern

| Concern | State | Evidence / verdict |
|---|---|---|
| Large lists | OK with `push_virtual_list` (uniform row height only); flat lists fine to about 10k cmds | measured: 10k rows = about 7 ms CPU; 50k = about 35 ms |
| Many text runs on screen | **Broken above 256 runs/frame** | measured; silent drop; also one GPU texture+bind group per string |
| Text editing | Minimal: single line, byte-indexed, no mouse caret/selection | code + issue #6; Kerf wrote its own `Editor` and still lacks multi-line chat input |
| IME | Win32 only; X11/web stub (issue #7) | `imeState()` returns `.{}` on web and X11 |
| Accessibility | Tree builder + web DOM mirror in zunk + Win32 UIA provider (read-only); **none wired into `teak.run`**, X11 no-op, no actions | grep of `run.zig` and the examples finds no `publishA11yTree` call; `win32.zig` UIA bridge present, untested here |
| Animation | None beyond frame counter and `Sub` | no easing/tween code; full-frame rebuild would make it cheap to add as Model-driven state |
| Retained caches | Text texture cache (256 entries), image cache (64 slots), mesh/image resources by key (128) | all fixed capacities |
| High DPI | Web done (CSS px, DPR division); Win32 deliberately deferred; X11 scale not verified | `docs/features/host.md` truth table |
| Multi-window | Win32 only | tasks.md |

### 2.4 Novel versus reinvented

- **Reinvented, usefully:** Elm architecture (Elm, iced, Bubble Tea), flat render commands (Clay, Dear ImGui draw lists), double
  buffering and frame diffing (React-ish, but done on flat data).
- **Genuinely distinctive in combination:**
  1. `Msg` values embedded in a flat, serializable command buffer, so hit-testing yields `Msg` and the whole frame is data.
  2. The GUI as text for agents (`TEAK_SNAPSHOT`, golden snapshots) plus headless native PNGs from the same `App`.
  3. HARDLINE as an audit-enforced design contract meant to stop an LLM-driven codebase from drifting into React.
  4. Comptime component stitching that synthesizes Model/Msg/update/view from a struct of components (already uses the 0.16
     `@Struct`/`@Union`/`@Enum` reification builtins).
- Clay is the closest conceptual sibling (layout emitting render commands); it has no state model and no WebGPU
  renderer in Zig. iced is the closest Elm sibling but is a retained widget tree in Rust.

### 3.2 Code quality (quick Zig-reviewer scan)

Good:
- Consistent design vocabulary, heavy doc comments that state invariants, comptime validators, no TODO/FIXME debris, zero `@panic`.
- Audit passes (`zig build audit`: module-scope `var` ban in core, no fn-pointer fields on Cmd, no platform imports in core,
  no `builtin` gating in core, view signatures, `llms.txt` coverage).
- Already modern on 0.16: `std.Io`-era clock, `@Struct`/`@Union`/`@Enum`, `@splat` in many places.

Concerns (counts via grep over non-test `src/`):
- 57 `catch unreachable` (44 in `core/cmd.zig`, on arena appends). `CLAUDE.md` documents this as policy ("arena OOM is unrecoverable"), but
  `unreachable` is undefined behaviour in release builds rather than an abort; one `oomAbort` helper would make the policy real.
- 78 `@ptrCast`, 16 `@alignCast`, 89 `anyopaque`, 114 `@intCast`, 196 `undefined`. Mostly in platform/GPU FFI and
  the type-erased `TextMeasurer`; reasonable for the domain but there is no ReleaseSafe test lane to catch a bad cast.
- Fixed capacities everywhere: 256 text runs, 64 images, 128 resources, nesting depth 32, 4 secondary windows, `ClipStack` and
  `FixedStack` asserts. Several fail silently (text) or only in Debug (stacks).
- Hash-keyed glyph cache entries are verified by `content_len` and `content_hash` (a second Wyhash), so collisions are guarded;
  the lookup is a linear scan over 256 entries per text draw.
- Win32 holds 29 module-level `var`s (allowed by HARDLINE in `platform/*`; typical for a WndProc but untestable).
- Per-frame heap churn: `Runtime` itself is allocation-light; `cmdsEqual` and double-buffered arenas are fine.

### 3.3 Tests and CI

- **Measured:** `zig build test` passes in about 30 s cold on this box; 407 `test` blocks in `src` plus 65 in `examples`/`test`,
  with 4.3K lines in dedicated test files. `zig build test-gpu` (real wgpu-native on Vulkan, 39 tests: depth, lighting, MSAA, images,
  overlay layering) passes on this machine.
- Strong coverage of layout (golden sizing tests), hit-test, run-loop routing (a scripted-host rig in `run_test.zig`), effects, snapshot.
- CI (`.github/workflows/ci.yml`) runs on ubuntu with Zig 0.16.0: library tests, audit (includes the wasm canary), and

- Missing coverage categories (the docs' own "host parity" test is listed as "does not exist yet"): cross-host input parity, a
  ReleaseSafe lane, a browser smoke test, fuzzing of layout/cmd buffers.

### 3.5 A verified defect: silent text drop above 256 runs

Reproduction (in a scratch copy, not committed): a vertical stack of 40 rows, each with 16 short text runs and a button
(640 text runs), headless native 1600x900. Rows 0-14 (about 250 runs) render; every later row renders no text at all. Cause:
`wgpu_core.uploadText` does `if (offset + 6 > self.text_verts.len) break; // text buffer full`, and `text_verts` is sized
`glyph_cache.CAPACITY * 6` (256 draws); `web.zig` has the same `TEXT_VERT_BUF_CAPACITY`. A second hazard: the 256-entry cache is
LRU with a linear scan, so a cyclic working set larger than 256 would thrash even if the vertex buffer were larger. Fix scope:
a real glyph atlas (per-glyph, colour in the vertex stream) with a growable vertex buffer; estimated 1 to 2 weeks including
the web backend, and it also fixes allocation of one texture plus one bind group per string.

### 3.6 Documentation and LLM-driven development

Verdict: **a real strength, with small drifts.**

- `llms.txt` (709 lines) is a single-read API pack, hand-curated, with an audit rule that fails the build if a `src/teak.zig`
  re-export is not named. Frontier models can work from it plus `docs/cookbook.md` (805 lines, 13 recipes verified against
  `src/`) and `docs/pitfalls.md` (real bugs with detection and root cause, e.g. slices into a by-value `Model` copy).
- `CLAUDE.md`/`AGENTS.md` give orientation; `docs/features/*.md` give a contract per public unit (about 3,900 lines).
- Evidence it works: Kerf's app (14,323 lines under `apps/teak/src`, about 250 + UI tests) was built in one day by an agent, including a
  chat harness, 3D view, exports and effects, with the agent also extending the framework (the "needed the most framework work" note).
- Drifts found: `llms.txt`'s "§2 Deliberate escape hatches" list stops at hatch 6 while HARDLINE has 8 (effects and resources are documented
  elsewhere in the file); README says "Seven examples" and lists eight; `tasks.md` "Next up" is stale relative to the Kerf push. Cheap
  to fix with an audit rule that counts hatches.
- Structural point: the paradigm is *simple enough to fit in a context window*, which is as important as the docs. A framework with
  two idioms (HARDLINE plus the 4-step recipe) is easier for a weaker model to use than egui's immediate-mode-with-memory or Compose's
  recomposition rules. The corpus problem is real (no Zig UI code in training data), and `llms.txt` is the right mitigation.

### 4.2 Where teak is uniquely valuable

- **"The small, LLM-drivable, Zig-native, WebGPU-on-web-and-native UI framework."** The conjunction is empty: dvui is not WebGPU-first and not
  Elm; Knots is early and immediate-mode; every Rust option brings a much larger toolchain and wasm.
- **Agent consoles and engineering tools.** Dense, mono-spaced, data-heavy UIs with an embedded 2D/3D viewport (`canvas`, `scene3d`) driven by
  an in-process Zig engine, with HTTP/LLM effects. Kerf is exactly this.
- **Deterministic, replayable, testable UIs.** A pure `Model`, `Msg` log and flat frame make record/replay, time-travel and snapshot
  diffing nearly free. iced and egui are working toward headless/AccessKit-based testing; teak has it by construction.
- **Footprint and build speed.** About 300 KB brotli framework baseline, 30 s cold test, 10 s native screenshot build. Zig's compile speed
  is a real daily advantage for agent loops compared with Rust's wgpu builds (the owner's own stack-strategy note concedes this).
- **Owning the whole stack.** teak + zunk + the Zig engine in-process, no JS, no Emscripten. The owner values this and the Kerf notes show it
  works end to end.

### 4.3 Where it cannot compete

- **General-purpose app UI with polished typography and international text.** Needs shaping, bidi, fallback, IME everywhere, and accessibility
  parity. Flutter, Compose, Slint and (eventually) Xilem will win; dvui or egui win in the Zig/Rust immediate-mode camp. A solo project will not close
  this gap on its own timeline.
- **Mobile.** Out of scope.
- **Consumer-grade accessibility compliance.** The AccessKit route covers native only, and there is no web adapter upstream; teak's own DOM mirror is
  the only web path and must be built and maintained.
- **Ecosystem and widgets.** No date pickers, rich-text editors, docking, charts beyond a line-chart helper.
- **Community scale.** The owner's own earlier assessment already names the community-friction factor; teak should be positioned as a *tool for the owner's
  products* that happens to be open, not as a platform that needs adopters.

## 5. Risks

### 5.1 Zig churn: measured 0.17 migration

Zig 0.17.0 is on the local box and (per ziglang.org via the survey) released on or about 2026-10-01. I copied teak and zunk to scratch directories
and migrated until everything I could run built and passed. Result: **a day of mechanical work, about half a day for an agent, and no design
change.** Evidence:

- Library `zig build test`: all 334 core tests plus platform/gpu-adjacent tests pass; `zig build test-wasm` and `zig build audit` pass; `zig build test-gpu`
  (39 real-GPU tests through the new translate-c module) passes.
- Chrome example: `zig build shot` on 0.17 produced a **byte-identical PNG** to the 0.16 build; `zig build web` on 0.17 produced a wasm that, run in Chromium, renders
  **identical pixels** to the 0.16 build (byte-identical screenshot file). Windows (`x86_64-windows-gnu`) cross-compiles; I did not run it.
- zunk: its CLI builds and its 42 tests pass on 0.17.

Edit inventory (all classified by cause):

| Class | Cause | Sites | Fix |
|---|---|---|---|
| Array repeat `**` removed | 0.17 removes `[_]T{x} ** N` and string `**` | about 25 in teak (`text_field`, `component`, `component_list`, `scene`, win32, tests, examples), 2 in zunk, 3 in owner's `rich_zig`/`webzocket` | `@as([N]T, @splat(x))`; multi-element repeats need an explicit literal or comptime loop |
| Reflection layout changed | `@typeInfo(T).@"struct".fields`, `.@"union".fields`, `std.meta.fields`, `.@"fn".params` replaced by parallel arrays (`field_names`, `field_types`, `field_attrs`, `param_types`) | about 40 sites, concentrated in `core/component.zig` and `core/component_list.zig` (the comptime stitching) | a 50-line `compat017.zig` shim exposing `fields(T)` and `params(F)`; the only genuinely non-trivial piece |
| `std.builtin.Type.StructField.Attributes`, `UnionField.Attributes` renamed | `Type.Struct.FieldAttributes`, `Type.Union.FieldAttributes` | 2 | rename |
| `@cImport` removed | wgpu-native and stb_truetype headers | 2 `@cImport` sites in source, 6 `build.zig` sites | `b.addTranslateC(...)` over a 2-line wrapper header, module imported as `wgpu-c` / `stb-c`; the in-tree TranslateC step still exists in 0.17.0 and worked first try |
| `b.args` removed | build system split (configurer/maker) | every `build.zig` (teak, zunk, 8 examples, `rich_zig`) | `run.addPassthruArgs()` |
| `builtin.mode` enum casing | `.Debug` becomes `.debug` | 2 | rename |
| `EnumSet.initEmpty()` | now `.empty` | 3 | rename |
| Enum reflection in build scripts / tests | `@typeInfo(E).@"enum".fields` | 2 | `field_names`/`field_values` |

Counted diffs: about 105 changed lines in `teak/src`, 17 in `teak/build.zig`, about 50 in examples, about 16 in zunk. The owner's dependencies
(`rich_zig`, `webzocket`) also need a trivial patch each, which blocks zunk until released. **Not done:** a native X11 window run on 0.17 (headless
native rendering is the same code path below the Host), Windows execution, browsers other than headless Chromium, and a full re-audit of semantic changes
(`@bitCast`, `errdefer` captures) beyond what the tests exercise.

Strategy: the cost is small enough that teak should **track the newest Zig once the dependency chain is green rather than ship a long-lived 0.16 line.**
Add 0.17 to CI as a second job; keep the `compat017.zig` shim isolated so the next reflection change is a one-file edit. The reflection change is the single
churn risk that touches the design (comptime stitching), and it did not break the design.

### 5.2 Other risks

| Risk | Severity | Notes / mitigation |
|---|---|---|
| **Bus factor** | high | One author; Oct 5 shows agents can produce 40+ commits a day, which raises review debt rather than lowering it. Mitigation: CI breadth (GPU, web smoke, Windows build), a ReleaseSafe lane, keep HARDLINE audit growing, write fewer features per month and more tests. |
| **Text/IME/a11y depth** | high | The three areas where UI frameworks are won or lost and where upstream Zig libraries are also weak (Knots and dvui both lack shaping/bidi). Needs a deliberate, scoped plan (section 6), not opportunistic fixes. |
| **wgpu-native pin** | medium | v25.0.2.2 versus upstream v29.0.x (secondary source). Updating means regenerating via translate-c (now easy) and checking `WGPU*` struct changes. Schedule one update per Zig release. |
| **WebGPU availability** | medium | Safari 26 and Chrome ship; Firefox on Linux/Android and Chrome on some Linux do not (survey). Decide: "WebGPU required" policy or a WebGL2/software fallback; today there is none. |
| **zunk coupling** | medium | Path dependency (`../zunk`), same author, young (single-day history in this repo). zunk is also the web a11y/IME/fonts bridge, so some "teak gaps" are zunk gaps. Pin by tag and publish when stable. |
| **Silent-failure fixed caps** | medium | Text 256 (verified), image 64, resources 128, nesting 32 (assert only). Make them fail loudly in release or grow. |
| **LLM-corpus risk for Zig** | medium | The owner's own assessment: models write worse Zig, and 0.15 to 0.17 churn makes stale training data actively harmful. `llms.txt` mitigates; version-pin every doc example and keep a per-release migration note (this review's table is a start). |
| **Maintenance cost** | medium | About 28K lines plus zunk's 8K plus vendored stb, three platform backends, two GPU backends. Each new capability must land three times (Win32, X11, web). Prefer cutting platform scope (see 6.3) over keeping all three half-finished. |
| **Strategic distraction** | medium | Kerf chose zig-ts (DOM) for the web product and kept teak as the "future native track". Teak competes with the owner's own pragmatic choice. It needs its own reason to exist (agent consoles, native tools, Zig-only products), not just parity with a DOM. |

## 6. Maturation roadmap (if continued)

Principle: fix the foundation that makes the existing demos honest, then deepen the niche (agent-driven tool UIs), then widen platforms only where
a product needs them. Each milestone ends with a Kerf-style acceptance app, not a feature list.

### M0: Stabilise (1-2 weeks)

- Zig 0.17 migration (section 5.1) and a 0.17 CI job; keep 0.16 until zunk, `rich_zig` and `webzocket` ship 0.17 patches.
- Fix the silent drops: remove the 256-run text cap (at minimum make it a loud Debug panic and a documented cap), raise or loudly overflow-check the 64-image and
  depth-32 limits, and make stack overflow a hard error in every optimize mode.
- Broaden CI: `test-gpu` on a software Vulkan (lavapipe) runner, a headless-Chromium web smoke test (screenshot hash, based on Kerf's `drive.mjs`), a Windows
  compile job, and a ReleaseSafe test lane. Pin zunk by tag.
- Generate `cmdsEqual` by comptime reflection. Fix `llms.txt` hatch count and README drifts, add an audit rule for them.
- Acceptance: `zig build ci-all` green on 0.16 and 0.17; the 640-run stress screenshot shows all text.

### M1: Text engine and text input (4-6 weeks) - the make-or-break milestone

- Glyph atlas (per glyph, subpixel positioning optional), growable vertex buffer, one draw per atlas page; the same design on web via zunk (either an atlas
  built from canvas-2D glyph rasterization or a shared stb path in wasm; decide by measuring wasm size).
- Text measure and wrap in layout (`text_wrapped`, max-width measure), flex shrink, min-content.
- `Editor`/`TextArea` component in the library (promote Kerf's): grapheme-aware cursor, selection by mouse and keyboard, word jumps, undo stack, single and multi-line, horizontal/vertical
  scroll, clipboard, key repeat. State lives in `Model`, view emits caret/selection data (stays within HARDLINE).
- IME: web hidden-textarea bridge (zunk composition events to `ImeState`), then X11 XIM or IBus, then verify Win32.
- Font stack decision: either vendor HarfBuzz + FreeType through translate-c (accept the C dependency, gain shaping/fallback/emoji) or declare "Latin/CJK-without-shaping" as the supported subset and
  say so in the README.
- Acceptance: Kerf's multi-line chat input and notes editor run on the library component with Japanese IME input working on web and one native host.

### M2: Widgets and lists (3-4 weeks)

- Variable-height virtual list and a real data table (sort, column resize, selection, keyboard nav), tree with virtualization.
- Rounded rects and soft shadows (SDF in the quad shader), per-corner radius, border styles, an `animate` helper (Model-driven tween driven by frame time), event-driven idle.
- Dropdown/menu/tooltip/popover polish on the overlay layer; focus ring and keyboard navigation audit.
- Acceptance: a 100k-row table scrolls at the display rate on web and X11; the `chrome` example gets a "modern" theme alongside the engineering one.

### M3: Accessibility (3-4 weeks)

- Wire `publishA11yTree` into `Runtime` (opt-in `RunOptions`), complete the zunk DOM mirror (focus sync, text-field value and selection, live regions, roles for table/tree/menu),
  and add action routing from the DOM back as `Msg`s (click, focus, set value) through the existing input path.
- Native: Win32 already has a hand-written UIA provider (wire it up and test with Narrator); for Linux consider AccessKit via its C bindings (AT-SPI); the survey reports Knots proving Zig can link it, with Linux limits to verify (glibc only).
- Acceptance: a screen reader (NVDA on web, Orca on X11) can operate the todo and chrome examples.

### M4: Platforms (4-6 weeks, only if a product needs them)

- Wayland (xdg-shell + libdecor via `dlopen`, matching the X11 no-dev-package approach), with a first-class clipboard and IME via text-input-v3.
- macOS: Cocoa host through the Objective-C runtime or a thin C shim, Metal via wgpu-native, CoreText or stb for text.
- Win32 DPI and parity (issue #5).
- Defer macOS unless a user needs it; Wayland before macOS for Linux-first agent tooling.

### M5: Agent DX as a product (ongoing, 2-3 weeks to a first cut)

- `teak inspect` over the snapshot stream: query by role/text, click/type by selector, record/replay a `Msg` log, screenshot diff, all via the headless host. Package it as an MCP server
  so a coding agent can run, look at and drive an app without a browser.
- Machine-readable `llms.txt` generation from doc comments (keep hand-curated prose, generate signatures) and a per-Zig-version migration note.
- Acceptance: an agent builds a new teak app from `llms.txt` alone and verifies it through the snapshot/screenshot loop in one session (repeatable eval, like Numen's dogfood rounds).

### 6.2 If not continued: alternatives, ranked

1. **Keep teak narrow ("apps for LLM agents" niche).** Freeze scope at M0 plus the headless/snapshot tooling and a minimal text-input fix; use it only for Kerf-class
   tool UIs and agent consoles where monospace, Latin text and a custom theme suffice. Lowest cost; honest about limits. This is the recommended floor.
2. **Adopt dvui** for general Zig GUI work. Most mature, active, supports web and AccessKit and IME; immediate-mode and WebGL-leaning, so teak's replay/snapshot advantages are lost. Contribute the
   things teak does well (headless screenshot, snapshot text) upstream if the owner wants impact without maintenance.
3. **Contribute to Mach.** Not recommended for UI: no web story, diverged from WebGPU, nightly-tied.
4. **Follow Knots.** Same rendering substrate, earlier, immediate-mode; worth watching and possibly sharing a text/atlas implementation rather than competing on it.
5. **Drop to DOM (what Kerf did) for web products and use teak only for native/desktop.** Reasonable product decision; it removes the web a11y/IME burden but also removes most of teak's unique pitch.

### 6.3 Recommended scope decision

Commit to M0 and M1 now (about 6-8 weeks). Review honestly after M1: if the text engine and a real `TextArea` run Kerf's chat and notes editor with web IME, continue to M2/M3 and treat
teak as a product; if M1 stalls, fall back to alternative 1 and stop adding platforms. Do not start M4 until a concrete product needs Wayland or macOS. Keep the claim in the README to
"WebGPU UI for tool-style apps, Zig-native, agent-friendly" until M3 lands.
